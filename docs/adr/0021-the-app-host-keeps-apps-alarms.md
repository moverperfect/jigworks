# The app host keeps apps' alarms

An app's Durable Object instances are facets (ADR 0015), and workerd refuses alarms in a facet: "Facets currently cannot set alarms" (#107, `docs/findings.md`). Deployed, the refusal is quiet after the first call: `getAlarm()` reads the time back, and the alarm never rings. Apps that do something at a set time, such as reminding someone the day before an event, need alarms. So the app host keeps them, and app code uses Cloudflare's own API: `this.ctx.storage.setAlarm(...)`, `getAlarm()`, `deleteAlarm()` and an `alarm()` handler. This amends ADR 0015, which listed alarms as not supported.

- **The instance's own storage holds its alarm.** The module the platform wraps the app in (`src/apphost/app-data.ts`) defines `setAlarm`, `getAlarm` and `deleteAlarm` on each instance's real `ctx.storage`: the `DurableObject` base class refuses a stand-in `ctx`. The alarm is a one-row table named `__jigworks_alarm` in the instance's own database. So it commits with the call's other writes, or is lost with them, as in a `transaction()` that throws. A table, not a key, so `storage.list()` never shows it.
- **The app host's row only wakes the instance.** It keeps one row per instance: slot, binding, ID, name and the time due. Its own alarm is set for the earliest due time of those rows and of its retired Secrets (ADR 0016). A row may be early or spurious: the instance decides whether to ring.
- **The protocol:**
  - `setAlarm` first tells the app host, through `AppData`, with the instance's binding, ID and name, which reach it in `ctx.props`. Only then does it write the alarm, at the time the app host answers with (see the limits below). If the app host can't be told, or refuses, `setAlarm` throws and nothing is written.
  - The app host keeps the earlier of the new time and its row's. The instance may not keep the new time: its call can still fail, as in a `transaction()` that throws. An early wake does no harm, as the instance answers with its own time. A row being rung is replaced by the new time, so an `alarm()` that sets the next isn't woken again at once. The ring's answer then brings the new row forward if the instance's own time is earlier.
  - A write whose call later fails leaves only a spurious wake, which finds no alarm and does nothing.
  - `deleteAlarm()`, when the instance has an alarm, first tells the app host, which moves the row to the minimum interval from now. That wake finds no alarm, so the row goes. If the call that deleted it fails, the wake finds the alarm and keeps it. The interval means the wake almost always comes after the call has committed. While it tells the app host, a wake doesn't ring. If the app host can't be told, the alarm is deleted all the same, and the row stays until its time.
  - `setAlarm`, `getAlarm` and `deleteAlarm` run one at a time in the instance, in the order they were called, so calls made without `await` keep their order, as on Cloudflare.
  - When a row is due, the app host calls the instance's platform-named method, `__jigworks_ring`: `alarm` itself can't be called over RPC. App code can't call that method through its binding.
  - The method rings `alarm({ retryCount, isRetry })` only if the instance's own alarm is due, or its last ring was cut off. It marks the alarm ringing first, so `getAlarm()` reads `null` during `alarm()`, unless `alarm()` sets a new one. Once `alarm()` returns, the alarm is cleared; if it throws, a retry takes its place (below).
  - The method answers with the instance's alarm's time now, or none, and any error `alarm()` threw. A `setAlarm` still telling the app host counts, so a wake that comes before that call writes its alarm doesn't lose it. The app host replaces its row with the answer, so the row is deleted only after the instance answers. Each `setAlarm` gives the row a new version, and a ring's answer replaces only the version it rang, so a `setAlarm` during a ring isn't overwritten.
  - An instance that can't answer, such as one whose code throws as it starts, is woken again with the backoff of a failing `alarm()` (below), up to 6 times. After that its row is deleted, and the slot's logs say so. A row whose binding has gone from the slot's code is deleted. In both cases the instance can't be told, so it keeps its alarm: if it runs again, or its binding comes back, `getAlarm()` reads a time that won't ring until the app sets one again.
  - Each ring goes to the slot's logs, with its retry count and how it ended: in how long it rang, or the error, and whether and when it will be retried. So does a ring past its deadline, and a wake the instance couldn't answer. The platform's own logs have a line for each wake that calls an instance, with its Workspace, slot, binding, outcome, retry count and duration. Neither has the instance's name, which may hold a person's details.
- **Retries,** so an alarm rings at least once, as on Cloudflare:
  - A failing `alarm()` is retried with `{ retryCount, isRetry: true }`, the first retry a minimum interval later, and each after twice as long as the one before: with the default interval, 1, 2, 4, 8, 16 and 32 minutes. After 6 retries the alarm is dropped, as Cloudflare drops it. Cloudflare's first retry comes 2 seconds later, but the interval holds retries too, and a backoff that starts there rides out an outage of an hour rather than two minutes.
  - The instance keeps the retry count with its alarm, and the time of the next retry, which `getAlarm()` reads. `setAlarm` and `deleteAlarm` replace a retry, as they would any alarm.
  - An `alarm()` that sets or deletes its alarm and then throws isn't retried: as on Cloudflare, retries are for the latest `setAlarm`.
  - The alarm stays marked ringing until `alarm()` ends. A ring cut off by a new Build, a publish or new Secrets, which stop the slot's instances, or by the app host stopping, leaves it marked. Its row was never answered, so it wakes the instance again: a minimum interval later, or as soon as the app host's own alarm runs again. The instance finds the mark and rings again as a retry, dropping the alarm if that ring was its last.
  - The app host sets its own alarm at most a year ahead, so an alarm too far ahead for workerd can't make it fail.
- **Limits,** so no app can use alarms to run constantly or hold up its app host. They're in the Installation's configuration (`wrangler.jsonc`), and the tests set lower values the same way (`vitest.config.ts`):
  - **A minimum interval,** `APP_ALARM_MIN_INTERVAL_MS`, 1 minute: an alarm set sooner rings at the interval, and `getAlarm()` reads that time. A ring's answer is held to the interval from that wake too, as app code can write `__jigworks_alarm` itself. So an instance rings at most 1,440 times a day.
  - **A cap per slot,** `APP_ALARMS_PER_SLOT`, 1,000: the most instances with a row in the slot. A `setAlarm` that would add one more throws, saying why, and nothing is written. Moving an instance's alarm doesn't count. A deleted alarm stops counting once its wake, at the interval, finds it gone. A row stays until it's woken, so an alarm set in a call that failed, or cleared by `deleteAll()`, counts until its time.
  - **Rings a few at a time,** 5, each within the app's limits (`appLimits`), as any call to the app is, and a deadline, `APP_ALARM_RING_DEADLINE_MS`, 30 seconds. A ring past it goes to the slot's logs and runs on. The app host stops waiting for it, but keeps its answer when it comes, and is kept running for one more deadline for it. In case none comes, as when the app host restarts, the row is woken a minute later. An instance isn't rung while it's still ringing, even for a next alarm it has set: its row is pushed back another minute.
  - **A wake ends within two deadlines,** and keeps the app host running for at most three. No ring starts once it has run for one. The rows left are still due, so the app host wakes again at once. So one app's slow `alarm()`s can't hold up the clean-up of retired Secrets for long, and a wake stays well within Cloudflare's 15 minutes for an alarm.
- **Data and code follow ADR 0015:** rows are per slot, an alarm rings with the slot's current code, alarms set before a new Build or a publish ring with the new code, and publishing doesn't copy alarms. Deleting the Workspace deletes the rows with the app host.
- **The Preview's alarms ring by themselves,** as the Deployment's do. The Developer sees an app's alarm work before publishing.

## Considered options

- **Cron triggers first.** They work through the app host too (#107). But "the day before each run" would mean polling, and they need a cron parser, time zones and limits of their own. The Build still fails on cron triggers.
- **The app host calling a route,** such as `POST /__scheduled`. Anyone with the app's URL could call it unless the wrapper blocked it, and it isn't how a Worker is written.
- **The app host's row alone,** as #107's probe did. A call that failed after `setAlarm` would still ring, and `deleteAll()` wouldn't cancel it, if facets had it.

## Consequences

- **At least once, as on Cloudflare.** A wake that comes before the call that set the alarm has committed, where that call then fails, rings once when it shouldn't have.
- **A `deleteAlarm` in a call that runs on for longer than the minimum interval and then fails** loses the alarm: the wake finds it deleted, before the call is undone.
- **Every `setAlarm`, and every `deleteAlarm` of an alarm, makes the hops a binding's call makes** (ADR 0015), to the app host and back. `getAlarm` stays in the instance.
- **An alarm set sooner than the minimum interval rings later than on Cloudflare,** where it would ring when due. So can an alarm due within the interval of a spurious wake, such as one left by a call that failed, or a `deleteAlarm` whose call failed.
- **An `alarm()` that never ends** holds only its own instance: it isn't rung again while it runs, and its row is woken every minute until the app host restarts.
- **One app's failing alarms can't hold up the rest:** a failing alarm is retried at most 6 times, over about an hour, and each ring is held to the app's limits and the deadline like any other.
- **`AppData`'s `setAlarm` and `deleteAlarm` are open to app code** through `env` imported from `cloudflare:workers` (ADR 0015), for its own slot. They can add a wake, or move one, and start an instance that was never used, but an instance rings only if its own alarm is due, and the wake's answer puts its row back.
- **`deleteAll()` clears the alarm,** as on Cloudflare, where it works in a facet (`docs/findings.md`, #144). Locally, workerd refuses `deleteAll()` in a facet (`test/app-data.test.ts`).
- **The platform relies on facet behaviour** that a workerd upgrade could change: methods defined on `ctx.storage` are the ones the app calls, `ctx.props` reaches the instance, and the platform-named method can call `alarm()`. `test/app-data.test.ts` pins each, and the test pinning workerd's own refusal stays, so an upgrade that gives facets alarms is noticed.
